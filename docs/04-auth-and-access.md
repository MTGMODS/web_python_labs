# Користувачі, ролі та розмежування доступу

Лабораторна робота №2. Мета — не «прикрутити логін», а закласти фундамент
взаємодії клієнтів із системою: хто може читати, хто писати, і як це перевіряється
на кожному запиті без збереження стану в процесі застосунку.

## 1. Дві ролі

| Роль | Хто | Що може |
| --- | --- | --- |
| `passenger` | клієнт | реєструється сам, шукає рейси, утримує місце, оплачує та скасовує **свої** квитки |
| `admin` | співробітник перевізника | створюється скриптом, керує розкладом, бачить усі квитки, може скасувати будь-який |

Реєстрація через API і форму `/register` завжди створює пасажира. Поле `role` у
запиті ігнорується — підвищити себе до адміністратора через контракт неможливо.
Адміністратор з'являється лише з `scripts/seed.py` або `scripts/create_admin.py`.

## 2. Чому JWT, а не сесія в пам'яті

Застосунок з лабораторної №1 залишений **stateless**: жоден стан запиту не живе
в словнику процесу. Сесія в Redis або в пам'яті uvicorn зламала б це рішення і
змусила б у наступних роботах клеїти sticky sessions на балансувальнику.

Токен доступу (JWT, HS256) несе `sub` (ідентифікатор) і `role`. Підпис перевіряється
локально, без запиту до бази на кожен виклик. Платою є затримка поширення зміни
ролі — до закінчення терміну життя токена (за замовчуванням 60 хвилин). Для
навчального навантаження це прийнятно: відкликання токена і чорний список — тема
наступних робіт.

Токен видається двома каналами:

- заголовок `Authorization: Bearer …` — для API і кнопки Authorize у Swagger;
- HttpOnly cookie `access_token` — для HTML-сторінок.

Ядро перевірки одне (`app/api/deps.py`). Відрізняється лише реакція на відсутність
токена: REST віддає **401**, сторінка — **302** на `/login`. Це два дозволені
варіанти з умови роботи.

Пароль зберігається лише як bcrypt-хеш. Повідомлення «невірний email або пароль»
однакове для обох помилок входу, щоб форму не можна було використати як перевірку
існування акаунта.

## 3. Де саме стоїть перевірка прав

```
клієнт
  → залежність FastAPI (токен → користувач → роль)
    → сервісний шар (чи належить квиток / профіль цьому користувачу)
      → обмеження бази (унікальний email, частковий унікальний індекс на місце)
```

Вертикальне розмежування (роль) перевіряється **до** тіла маршруту:
`AdminUser` і `dependencies=[Depends(require_admin)]` на роутері `/admin`.
Новий адміністративний шлях неможливо додати «забувши» перевірку.

Горизонтальне розмежування (IDOR) перевіряється в сервісі, а не в роутері:

- `users.update_profile` — пасажир змінює лише `actor.id == user_id`;
- `booking._get_ticket_for_actor` — пасажир працює лише зі своїм квитком.

Чужий ресурс дає **403**, не 404: умова роботи вимагає саме цей код. Перевірка
прав іде раніше за перевірку існування профілю, щоб не підтверджувати сторонньому
користувачу наявність чужого ідентифікатора.

## 4. MVP предметної області

Ланцюжок, без якого система ще не продає квитки:

1. `POST /api/v1/trips/{id}/seats/{number}/hold` — місце `free → held`, з'являється
   квиток зі статусом `held` і терміном `held_until` (10 хвилин).
2. `POST /api/v1/tickets/{id}/pay` — квиток `paid`, місце `sold`.
3. `POST /api/v1/tickets/{id}/cancel` — квиток `cancelled`, місце знову `free`.

Арбітр конкуренції — база, не застосунок. Рядок місця блокується
`SELECT … FOR UPDATE`; паралельний запит на те саме місце чекає зняття блокування
і отримує 409. Друга межа — частковий унікальний індекс
`uq_tickets_active_seat` (один нескасований квиток на місце). Обидва механізми
працюють однаково при будь-якій кількості екземплярів FastAPI.

Протерміноване утримання знімається «ліниво» в момент наступного звернення до
місця. Фоновий воркер для масового прибирання — наступні роботи.

Адміністратор додає рейс і змінює статус розкладу. Місця нового рейсу генеруються
з шаблону салону за правилом дальності з лабораторної №1.

## 5. Домашні сторінки-заглушки

| URL | Хто | Що показує |
| --- | --- | --- |
| `/home` | пасажир | власні квитки та дозволені дії |
| `/admin` | адміністратор | лічильники користувачів, маршрутів, рейсів і квитків |

Анонім на `/home` отримує 302. Пасажир на `/admin` — сторінку 403, не редірект:
вертикальне розмежування має бути видимим і на HTML, і в API
(`GET /api/v1/admin/home` → 403).

## 6. Що свідомо відкладено

Відкликання токенів, refresh-токен, двофакторна автентифікація, реальний платіжний
шлюз, фонове зняття прострочених `held`, WebSocket схеми салону. Усе це нарощується
на вже існуючі ролі та залежності, без переписування моделі доступу.
